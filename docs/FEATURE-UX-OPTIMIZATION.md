# 功能与用户体验优化建议

> 评估对象：智能自适应 AI 面试系统（`java-backend` / `python-ai` / `code-runner` / `web` + PostgreSQL(pgvector) + Redis）
> 评估方式：全量静态阅读前端页面与组件、Java 控制器/服务、Python Agent 与 Prompt、SQL 与编排配置
> 文档定位：从**产品功能与用户体验**出发，回答「哪些地方让用户卡住、困惑、丢失成果，应该补什么功能」
> 配套文档：安全、性能、工程质量类问题见 [`docs/OPTIMIZATION.md`](./OPTIMIZATION.md)，本文只引用不重复
> 日期：2026-11-19

## 0. 摘要

### 0.1 三条总体结论

1. **主链路是完整的，但「可恢复性」不足。** 简历/JD → 自适应面试 → 六维评测 → 复盘报告 → 长期画像 → 八股拷打已经跑通；然而一次网络抖动、一次 AI 超时或一次页面刷新，就可能让用户丢掉刚写的答案、看不到报告，甚至把会话卡死。
2. **AI 已经产出了大量可解释信息，但前端只展示了约一半。** 缺口分析（`GapAnalysis`）、评分依据（`basis`）、遗漏知识点（`missed_knowledge_points`）、参考答题要点（`reference_points`）、逐题决策理由、LLM 调用耗时都已在数据链路中，却大多停在接口返回里，用户看不到。
3. **学习闭环停在「报告」这一页。** 报告里的短板与训练计划是纯文本，不能一键开练；错题不能收藏复习；八股 15 个标签中有 3 个缺少领域 Skill 上下文。用户「测—评—练」的最后一公里没有打通。

### 0.2 最快见效的七件事

| 顺序 | 建议 | 用户感知 | 工作量 |
| --- | --- | --- | --- |
| 1 | **R-01 会话韧性**：失败保留草稿、解锁输入、可重试/同步 | 不再「答了白答」 | M（前端 S + 后端 M） |
| 2 | **R-02 报告可回看**：`/report/:id` 深链 + 历史入口 | 刷新不丢报告 | S |
| 3 | **R-07 等待反馈**：分阶段文案 + 骨架气泡 + 可离开 | 长等待不再像卡死 | S–M |
| 4 | **R-04 评测详情展开**：得分依据、遗漏点、参考要点 | 每答一题都能学到东西 | S–M |
| 5 | **R-05 解析结果预览**：简历/JD 解析结果可见可纠正 | 开面前就能发现「解析歪了」 | S（只读） |
| 6 | **R-06 历史与会话管理**：搜索/筛选/重命名/删除/继续 | 历史从「只读列表」变成资产 | M |
| 7 | **R-03 开前缺口分析卡**：匹配度、优势、薄弱、重点考察 | 知道这场面试为什么这样问 | M |

## 1. 现状诊断

### 1.1 用户旅程与摩擦点

| 阶段 | 用户目标 | 当前实现 | 主要摩擦 |

### 1.4 优先级判定

| 级别 | 判定标准 | 覆盖问题 |
| --- | --- | --- |
| **P0** | 阻断主链路、造成成果丢失或数据不一致；修复成本可控；用户每天都会遇到 | F-01～F-09、F-12 |
| **P1** | 明显影响效率或学习效果；需要新增中等规模接口/页面 | F-10、F-11、F-13～F-16、F-17（训练闭环部分） |

> 说明：P0 不等于「代码改动最小」，而是「不修就会持续伤害用户信任」。例如 F-02 需要后端恢复入口，但前端丢稿可以先独立修，二者可分两步交付。

## 2. 产品主题与设计原则

### 2.1 五个产品主题

1. **闭环（测—评—练）**：一场面试的终点不应是报告，而应是「下一步练什么」。
2. **可控（用户掌舵）**：题量、难度、是否代码题、何时结束、是否重试，用户应有明确控制权。
3. **可信（可解释 AI）**：每个分数、每道题、每次追问都能回答「为什么」。
4. **沉淀（长期资产）**：报告、错题、画像、训练记录应可回看、可检索、可导出。
5. **可运营（本地可维护）**：知识库、题库、Skills、索引状态应能在界面内维护，不依赖手工 SQL。

### 2.2 设计原则

- **失败不惩罚用户**：网络/AI 失败时保留输入、保留现场、提供重试；不要用「重新开始」作为唯一出路。
- **渐进披露**：评测详情默认折叠，愿意深挖的用户一键展开；不要让信息量压垮答题节奏。
- **等待要诚实**：能给出阶段就给阶段，不能给就用不确定进度 + 计时 +「可离开」提示，不伪造百分比。
- **默认值优先**：配置项默认「自动」，高级选项折叠；普通用户不配置也能获得完整体验。
- **先复用再新建**：报告、轮次参考要点、评测依据、知识库/题库 CRUD 大多已存在，优先补入口与展示，避免重复造轮子。
- **本地优先与隐私**：所有数据默认留在本机；导出/清除能力与数据同等重要。

## 4. P0：快速见效

### R-01 会话韧性：失败保留草稿、输入解锁、可重试与状态同步

**问题与证据**

- `InputBar.vue:12-20` 在调用提交前执行 `text.value = ''`，请求失败后草稿已不可恢复。
- `session.js:349` 在请求前把 `inputEnabled` 置为 `false`；`catch` 分支只移除 loading 气泡并 `throw`（`355-358`），没有任何路径把它设回 `true`。用户只能刷新或结束。
- 服务端 `InterviewService.java:217-227` 先 `setAnswer` 并 `updateById`，再调用 AI；AI 失败后该轮不再是「开放轮次」，而 `requireOpenTurn` 只查 `answer IS NULL`（`655-669`），重试必然报错。
- 前端默认超时 90s（`client.js:13`），后端 AI 读超时 120s（`application.yml:44`、`AiServiceClient.java:48`）。前端先中断时，后端可能已完成并推进到下一题，造成「客户端失败、服务端前进」的隐性不一致。
- `ui.js:17-28` 的全局 `busy` 锁在整个请求期间生效，导致评测中「结束面试」「请求提示」都被拒绝，用户被锁在流程里。

**方案**

1. **前端提交态机**：`idle → submitting → success / failed`。
   - 草稿只在 `handleDecision` 成功返回后清空；失败时恢复原文并聚焦。
   - 候选人气泡先以「待确认」样式加入；失败时标记「未送达」并提供「重试」按钮，重试复用同一 `turnNo` 幂等键。
   - `catch` 中恢复 `inputEnabled = true`，并显示可关闭的错误横幅（区分超时/断网/上游错误）。
2. **锁粒度**：把全局 `busy` 改为「按动作加锁」（提交、提示、结束各自独立），或允许长请求期间执行「结束」与「同步状态」。
3. **超时对齐**：`/answers` 与 `/finish` 使用 180s（高于后端 120s + 余量）；其他接口维持 90s。超时文案明确「AI 仍在处理，可稍后同步」。
4. **服务端恢复入口**：

   - 新增 `GET /api/interviews/{id}/state`：一次性返回 session + turns + evaluations，供前端「同步会话状态」。
5. **前端恢复入口**：错误横幅与顶栏都提供「同步状态」；同步后若服务端已进入下一题，自动渲染最新开放题；若报告已生成，跳转 `/report/:id`。

**用户价值**

把「一次失败 = 一场作废」变成「一次失败 = 点一下重试」。这是用户对系统可靠性最直接的体感，也是本地部署环境下网络/模型波动时的必需能力。

| 层 | 文件/接口 | 改动 |

### R-02 报告可回看：深链、历史入口与刷新恢复

**问题与证据**

- `ReportView.vue:11-12` 只读 `session.lastReport`（Pinia 内存），`40-44` 在为空时直接展示「尚无报告」。
- `router/index.js:8` 的 `/report` 没有 `:id`，刷新后没有任何恢复依据。
- 报告其实已经落库：`InterviewService.java:510-539` 把 `report` 写入 `interview_session.report`，`GET /api/interviews/{id}`（`InterviewController.java:71`）可返回；**这是路由与入口问题，不是持久化问题**。
- 历史行点击只加载 turns/evals 进入回放（`HistoryView.vue:81-87`、`133-146`），已完成会话没有「查看报告」入口。

**方案**

1. **路由**：新增 `/report/:id`，保留 `/report` 作为「最近一场报告」兼容入口（从 `localStorage` 取最近 session id，取不到则展示空态）。

3. **场景判定**：从 `session.plan.mode === 'GAUNTLET'` 派生场景，不再依赖内存 `scene`。
4. **入口统一**：
   - 面试结束/提前结束：`router.push({ name: 'report', params: { id: sessionId } })`。
   - 历史列表：已完成行主操作「查看报告」，次操作「回放」；RUNNING 行主操作「继续面试」。
   - 画像页/报告页提供「最近报告」快捷入口。
5. **状态处理**：若 `status === 'RUNNING'` 且无 report，展示「本场尚未结束，继续面试 / 结束并生成报告」而不是空白。

**用户价值**

报告从「一次性页面」变成可回看、可书签、可对比的长期资产；也修复了「历史点进去只有回放、以为报告丢了」的认知错误。

**实现要点**

| 层 | 文件/接口 | 改动 |
| --- | --- | --- |
| 前端 | `router/index.js`、`ReportView.vue` | `:id` 路由、按 id 拉取、骨架/空态/场景派生 |
| 前端 | `session.js`、`HistoryView.vue`、`InterviewView.vue` | 结束跳转带 id；历史入口语义；RUNNING 处理 |
| 后端 | `GET /api/interviews/{id}` | 已具备，无需新增 |

**工作量**：S

**验收标准**

- 在报告页刷新、复制链接新开标签页、前进/后退，均能正确展示同一份报告。
- 历史中任意 COMPLETED 会话可一键进入对应报告。

**依赖与风险**

### R-03 开前缺口分析卡：让用户知道「为什么考这些」

**问题与证据**

- `director.py:23-28` 已实现 `analyze_gap(resume, jd)`，`GapAnalysis`（`schemas.py:53-58`）包含 `match_score`、`strengths`、`weaknesses`、`key_inspection_points`。
- 但 `make_plan`（`director.py:31-48`）只返回 `InterviewPlan`，gap 被丢弃；`/ai/interview/start` 的响应只含 `plan` 与首题（`python-ai/app/api/interview.py:38-61`），前端完全不可见。
- 准备页只在开始按钮旁写「系统将根据简历-JD缺口分析自动规划」，用户无法在开面前看到分析结果（`StartPanel.vue:65`）。

**方案**

1. **新增预览接口**：
   - Python：`POST /ai/interview/gap`，入参 `resume`、`jd`、`profile`，返回 `GapAnalysis`。
   - Java：`POST /api/interviews/gap-analysis`，入参 `candidateId/resumeId/jdId`，负责取数、归属校验、缓存与转发。
2. **缓存**：以 `resumeId + jdId + profile 版本` 为 key 存 Redis（TTL 24h）；同一组合重复预览不再消耗 LLM。
3. **准备页交互**：
   - 简历与 JD 都选中后，展示「分析岗位匹配度」按钮（显式触发，避免每次选择都烧 token）。
   - 结果卡展示：匹配度环形/进度、优势（绿）、薄弱/缺口（橙）、重点考察（蓝）、预计题量与主题。
   - 底部主按钮「按此计划开始面试」，次按钮「重新分析」。
4. **计划复用**：`start` 请求可携带 `gap` 或 `gapToken`；`make_plan` 优先使用已确认的 gap，避免二次分析；并把 gap 写入 `plan.gap` 持久化，供报告与历史对比。
5. **降级**：gap 接口失败时不影响开始面试，展示「本次跳过缺口预览」并直接走原流程。

**用户价值**

把面试从「黑盒出题」变成「有依据的考察」；用户能在开前发现「这个 JD 解析得不对」或「我的优势没被识别」，也更容易接受后续的高难度追问。

**实现要点**

| 层 | 文件/接口 | 改动 |
| --- | --- | --- |
| Python | `app/api/interview.py`、`app/agents/director.py` | 新增 `/ai/interview/gap`；`make_plan` 支持传入 gap |
| Java | `InterviewController.java`、`InterviewService.java`、`AiServiceClient` | 新增 `/gap-analysis`，取数 + 缓存 + 转发 |
| 前端 | `SetupView.vue`、`StartPanel.vue`、`session.js` | 分析按钮、结果卡、确认后开始、错误降级 |

**工作量**：M

**验收标准**

- 选好简历+JD 后可看到匹配度、优势、薄弱、重点考察。
- 第二次分析同一组合 <500ms（命中缓存）。
- 开始面试后，`session.plan.gap` 存在，且计划主题与重点考察一致。
- gap 接口失败时仍可正常开始面试。

**依赖与风险**

- 首次分析增加 3–10s 等待，需要 R-07 的等待反馈配合。
- gap 质量依赖简历/JD 解析质量，需与 R-05 一起做。
- 不要让「分析」变成开始面试的强制门槛。

### R-04 评测详情展开：得分依据、遗漏知识点与参考要点

**问题与证据**

- 前端只渲染总分、六维、清单与 issues（`session.js:283-303`），且 issues 的证据只截取 90 字。
- 后端 `EvaluationOut` 已包含 `basis`（得分依据）、`missed_knowledge_points`（遗漏知识点）、`evidence`、`checklist`、`follow_up_direction`（`schemas.py:117-135`）。
- `interview_turn` 已存 `reference_points`（`InterviewService.java:557`），`Evaluation` 实体存了 basis/issues/evidence/checklist（`Evaluation.java:32-41`），**唯独没有 `missed_knowledge_points`**。
- `handleDecision` 返回的 `evaluation` 对象本身包含遗漏点，只是前端没展示；逐题精讲几乎可以纯前端完成，只有「回放时仍可看」需要补持久化。

**方案**

1. **本轮评测卡改为可折叠**：
   - 收起态：总分 + 六维迷你条 + 一句结论（来自 `decision_reason`）。
   - 展开态：
     - **得分依据**：`basis` 逐条列出（答对了什么）。
     - **遗漏知识点**：`missed_knowledge_points` 以标签形式展示，点击可复制/加入错题本。
     - **问题与证据**：`issues` + `evidence` 一一对应，保留更多原文（建议 160–200 字）。
     - **参考答题要点**：当前题的 `reference_points`（从 `renderQuestion` 时缓存的 `currentQuestion` 读取）。
     - **要点命中清单**：现有 checklist，标注 full/partial/none。
     - **提示与用时**：`hint_count`、`meta.llm_elapsed_ms`（可选显示）。
2. **持久化遗漏点**：给 `evaluation` 增加 `missed_knowledge_points JSONB`（幂等 `ALTER TABLE ... ADD COLUMN IF NOT EXISTS`），`Evaluation` 实体与 `applyAiDecision` 写入；`ReplayView` 复用同一展示组件。
3. **组件化**：抽出 `EvaluationDetail.vue`，面试现场与回放/报告共用，避免三套渲染逻辑。
4. **渐进披露**：默认收起，避免每轮信息过载；提供「本场全部展开」开关。

**用户价值**

「答完即学」：用户不用等报告就知道自己漏了哪个知识点、哪句话是错误证据、参考答案的要点是什么。这是评测产品与普通打分器最大的差异点。

**实现要点**

| 层 | 文件/接口 | 改动 |
| --- | --- | --- |
| 前端 | `session.js`、`MsgBubble.vue`、新增 `EvaluationDetail.vue` | 缓存当前题参考要点；折叠卡；证据全文 |
| 前端 | `ReplayView.vue`、`ReportView.vue` | 复用详情组件 |
| 后端 | `Evaluation.java`、`InterviewService.java`、`init/sql` | 补 `missed_knowledge_points` 字段与写入 |
| 数据 | `evaluation` 表 | 幂等加列；旧数据为空时隐藏该区块 |

**工作量**：S–M（纯前端展示 S；持久化 S）

**验收标准**

- 每轮评测可一键展开/收起，展开后能看到依据、遗漏点、证据原文、参考要点。
- 刷新后从历史回放仍能看到遗漏点（新会话）。
- 移动端展开不遮挡输入区，滚动位置合理。
- 旧数据无遗漏点时页面不报错。

**依赖与风险**

- 参考要点在题目下发时才有，前端需在 `renderQuestion` 时保存；刷新恢复时从 `turns` 读取。
- 信息过多可能干扰答题节奏，必须默认折叠。

### R-07 等待反馈：阶段文案、骨架气泡与「可离开」

**问题与证据**

- 开始面试只显示一条静态「正在分析简历与岗位缺口，生成面试计划…」（`session.js:400`），八股同理（`427`）。
- 首题链路是串行的 plan → question，`OPTIMIZATION.md` §4 第 3 条估计首题可见 3–6s；期间没有骨架、没有计时、没有阶段。
- 每轮评测只有「评测中」三个字（`session.js:350`），而一次作答最坏可能多次 LLM 往返（`OPTIMIZATION.md` §2.1），用户不知道还要多久。
- 没有「离开页面后回来继续」的提示；用户切走再回来，可能看到空白或旧状态。

**方案**

1. **开始面试**：
   - 进入面试页后立即展示面试官骨架气泡与阶段条：`解析简历 → 匹配岗位 → 规划主题 → 生成首题`。
   - 阶段文案用「当前进行到」而非伪造百分比；超过 8s 追加「模型响应较慢，仍在处理」。
   - 首题到达后骨架平滑替换为题目，避免布局跳动。
2. **每轮评测**：
   - loading 气泡显示计时（如「评测中 · 12s」）与当前阶段（`六维评分 → 生成追问 → 下一题`）。
   - 超过 20s 显示「可以离开此页，完成后在历史中查看 / 同步状态」；配合 R-01 的 `state` 接口。
   - 超过前端超时前给出「仍在处理」而非直接报错。
3. **结束/报告**：
   - 生成报告时展示阶段（`汇总轮次 → 归纳短板 → 生成训练计划`），完成后 toast + 标题徽标。
   - 若用户离开，报告落库后可在历史/最近报告入口看到。
4. **无障碍**：loading 区域加 `aria-live="polite"`，让屏幕阅读器感知状态变化。

**用户价值**

把「不知道在等什么」变成「知道在等什么、可以等或先走」；长等待不再等于卡死，用户对系统性能的容忍度显著提高。

**实现要点**

| 层 | 文件/接口 | 改动 |
| --- | --- | --- |
| 前端 | `InterviewView.vue`、`ChatFlow.vue`、`MsgBubble.vue` | 骨架气泡、阶段条、计时、`aria-live` |
| 前端 | `session.js` | 阶段状态机；loading 消息携带 startTime/stage |
| 可选后端 | `GET /{id}/state` | 支持离开后同步（与 R-01 共用） |

**工作量**：S–M

**验收标准**

- 开始面试后 200ms 内出现骨架与阶段，首题到达后无布局跳动。
- 评测 loading 显示计时，超过 20s 出现「可离开」提示。
- 离开再回来可通过历史/同步恢复，不出现空白页。
- 阶段文案不伪造百分比，不承诺无法保证的剩余时间。

**依赖与风险**

- 后端没有真实阶段事件，阶段只能按时间推断；文案需避免让用户误以为精确。
- 若后续做 SSE（R-16），阶段可直接由服务端事件驱动。

**问题与证据**

- 代码面板只能选择一个样例作为 stdin 运行（`CodePanel.vue:20-38`、`68-96`）；`runCode` 只保存最后一次执行结果（`session.js:458-487`）。
- 题目数据包含 `test_cases[].input/expected`（`schemas.py:63-65`），但前端从不比较 `expected` 与实际输出。
- 作答语言由题目决定（`enterCodeMode` 取 `data.language`），用户不能切换；切换后 starter code 与评测语言也没有约定。
- 草稿不保存：切题/刷新/失败后代码丢失；CodeMirror 从 CDN 加载（`index.html:8-12`），离线时降级为 textarea（`CodePanel.vue:31`、`77-84`；可编辑但失去高亮与缩进）。

**方案**

1. **运行全部样例**：
   - 「运行全部」逐个执行 `test_cases`，以表格展示 `# / 输入 / 期望 / 实际 / 结果`；空白归一化后比较。
   - 单样例仍可运行；结果保留在 `code.results[]`，提交时汇总「通过 3/4」作为评测证据。
2. **语言切换**：
   - 允许在题目未提交前切换语言；切换时提示「将替换为对应语言模板」，保留用户代码到本地草稿。
   - 提交时把 `language` 一并传给后端（扩展 `execution.language` 已有），评测 Prompt 明确语言。
3. **草稿保护**：
   - 按 `sessionId + turnNo` 自动保存代码与 stdin 到 localStorage；重新进入/刷新恢复；提交成功后清理。
   - 提供「重置为初始模板」与「插入样例输入」。
4. **离线可用**：
   - 将 CodeMirror 5 作为 npm 依赖打包（或本地静态资源），CDN 作为可选加速；保留 textarea 降级。
5. **体验细节**：
   - 显示运行耗时/退出码/超时；错误输出高亮；长输出可折叠/复制。

**用户价值**

代码题是技术面试的高压环节，减少「样例没跑全」「代码丢了」「编辑器没高亮」带来的非能力性失分。

**实现要点**

| 层 | 文件/接口 | 改动 |
| --- | --- | --- |
| 前端 | `CodePanel.vue`、`session.js` | 全样例执行、结果表、语言切换、草稿 |
| 前端 | `index.html`、`package.json`、`vite.config` | 本地化 CodeMirror |
| 后端 | `AnswerRequest.execution` | 已支持 language/stdout/exit_code；补 `results` 数组（可选） |
| Python | `evaluator` Prompt | 接收全样例通过情况（可选） |

**工作量**：M

**验收标准**

- 一键运行全部样例并显示期望/实际/通过状态。
- 切换语言后模板与高亮同步；提交语言与编辑器一致。
- 刷新/切题后草稿恢复；提交成功后不残留。
- 无网络时编辑器仍可用（本地资源或降级）。

**依赖与风险**

- 沙箱以 stdin/stdout 为契约，函数式题目需确保样例输入格式一致；展示时说明「按 stdin 运行」。
- 全样例执行会增加沙箱并发，需限制并发与超时（参考 `OPTIMIZATION.md` §1.5）。

## 7. 横向能力

### 7.1 错误分类与降级策略

当前 `client.js` 已归一化 `status/errorCode`，但 `ui.guard` 只把 `e.message` 塞进 3.2s Toast（`ui.js:17-28`、`Toast.vue`）。建议建立「错误类型 → 用户动作」映射：

| 错误类型 | 判定 | 展示 | 动作 |
| --- | --- | --- | --- |
| 网络离线 | `TypeError`/`Failed to fetch` | 顶部横幅「网络已断开」 | 恢复后自动同步/重试 |
| 请求超时 | `AbortError`/504 | 横幅「AI 仍在处理」 | 同步状态/重试；保留草稿 |
| 上游模型错误 | 502/`AI_UPSTREAM` | 卡片「模型服务异常」 | 重试/切换模型（管理员） |
| 参数/状态冲突 | 400/409 | 行内提示 | 修正后重试；说明原因 |
| 未登录/过期 | 401 | 跳转登录 | 已实现静默 refresh |
| 无权限 | 403 | 页面空态 | 返回/切换账号 |
| 限流/预算 | 429/`AI_BUDGET` | 提示「本场调用较多」 | 等待/结束面试 |

原则：**可恢复错误不用 Toast 打发用户**；页面内保留上下文与下一步按钮。

### 7.2 草稿保护矩阵

| 内容 | 存储位置 | 清理时机 | 备注 |
| --- | --- | --- | --- |
| 文字答案 | localStorage：`draft:{sessionId}:{turnNo}` | 提交成功 / 切换轮次 | 失败恢复；跨刷新 |
| 代码 + stdin | 同上，按 `turnNo` | 提交成功 / 重置 | 与语言一起存 |
| 实时语音转写 | 内存 + 可选 localStorage | 确认提交 / 取消 | 静默后先确认 |
| JD 粘贴文本 | localStorage 临时键 | 解析成功 / 离开页面后保留 1 天 | 防止误刷新 |
| 面试配置 | localStorage 全局键 | 不清理 | 记住上次选择 |

### 7.3 埋点与度量（本地优先）

无需引入第三方分析。建议新增轻量 `app_event` 表或结构化日志，记录：

- `interview_start`（scene、配置、gap 是否有）
- `first_question_visible`（耗时）
- `answer_submit`（结果、耗时、是否重试、错误类型）
- `report_view`（来源：结束页/历史/直接链接）
- `practice_start`（来源：报告训练计划/八股页/推荐）
- `wrong_book_add` / `wrong_book_review`
- `admin_action`（上传/重建/删除）

用途：验证第 9 节指标；本地单用户场景也可直接在前端 `performance` + `console.info` 起步。注意不要记录答案全文与密钥。

### 7.4 可访问性基线

- 所有交互元素可键盘到达，焦点样式可见（当前部分按钮依赖 hover）。
- Toast/评测加载使用 `aria-live="polite"`；错误使用 `role="alert"`。
- 图标按钮必须有 `title`/`aria-label`（现有部分已有）。
- 颜色不作为唯一信息载体（分数色阶同时显示数字/文字）。
- 尊重 `prefers-reduced-motion`（已有，继续覆盖新动画）。

### 7.5 数据备份、导出与清除

- 报告导出 Markdown；候选人画像/错题本导出 JSON。
- 提供「导出全部数据」与「清空我的数据」（输入确认词），并说明 Docker 卷位置。
- 删除候选人/会话时明确级联范围；软删除可降低误操作成本。

## 10. 不做清单与风险

### 10.1 明确不做

- 不做公网多租户、计费、组织权限体系；保持本地单用户/小团队定位。
- 不做视频面试、实时音视频、虚拟形象。
- 不引入 K8s、消息队列、独立向量数据库替换 pgvector 等重型基础设施。
- 不重写现有 UI 设计语言；以增量组件与入口为主。
- 不在本文重复安全/性能治理项（见 `OPTIMIZATION.md` §1/§2）。

### 10.2 主要风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| 配置项过多导致准备页复杂 | 用户放弃配置 | 默认「自动」+ 高级折叠 + 三个预设 |
| 伪造进度条损害信任 | 用户反感 | 只做阶段文案 + 不确定进度 + 计时，不承诺百分比 |
| 重试导致重复 LLM 成本 | 成本上升 | 幂等键、次数上限、失败原因明确 |
| 报告/错题数据删除不可逆 | 数据丢失 | 二次确认 + 软删除/导出兜底 |
| 学习模式被当成正式成绩 | 统计失真 | 八股不计画像（已有）；学习模式单独标记 |
| Skill 内容质量不足 | 出题泛化 | 先补 3 个缺失领域，建立评审清单与覆盖检查 |
| 深链权限校验遗漏 | 越权查看 | 复用 `Ownership.check`；报告/回放统一校验 |
| 范围蔓延 | 交付延期 | 按批次退出标准验收；P2 不阻塞 P0/P1 |

### 10.3 需要产品决策的点

1. 错题本存后端还是本地？建议后端（可统计、可跨浏览器），但增加一张表与 CRUD。
2. 学习模式是否允许在看答案后标记「已掌握」？建议允许，但单独统计。
3. 报告是否允许匿名分享链接？本地定位下建议先不做，仅支持导出。
4. 八股标签上限是否从 6 放开？建议保持 6，增加「随机 3 个」而非无限多选。

## 12. 结语

这个项目已经具备一个「能跑完整场面试」的骨架，下一步的竞争力不在更多 Agent，而在**把已有能力交付到用户眼前**：让失败可恢复、让报告可回看、让评分可解释、让训练可执行。建议按「第 0 批止血 → 第 1 批可信可控 → 第 2 批学习闭环 → 第 3 批打磨」推进；每一批都以本文第 9 节的指标验收，而不是以「功能上线」验收。
